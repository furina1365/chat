# 完成开发并交付文档

当用户要求实施时，在同一轮完成调查、实现、测试和文档。自行处理范围内的实现细节、测试环境准备、失败诊断和重跑。需要用户决定业务行为、授权或提供无法替代的环境时，先推进独立工作，再指出具体待办。用户只要求分析、评审或方案时，按其要求交付。

## 开发顺序

1. **背景与现状**。先查与任务相关的可用知识库和项目文档，确认业务目的、系统边界和术语。沿正常入口读当前代码、已有测试和相关 Git 历史，记录改动前的调用链和决策流程。背景只写业务与系统事实。事实缺少依据时保留为待确认项。
2. **需求与判断**。列出用户直接提出的显性需求，以及从既有行为、兼容性和约束推断的隐性需求。给推断注明依据。把关键问题、选定的答案和依据串成判断链，说明前一个判断怎样影响后续选择。用可观察的行为描述验收条件。
3. **切片与实现**。每片从触发走到可观察结果，能单独上线和验收，覆盖一条判断链，并且没有可独立交付的更小部分。每片明确对应的判断及所采用的答案。找不到对应判断时，补足决策依据或移出方案。跨入口、校验、存储和通知的改动可以属于同一切片。沿正常入口实现，保留既有调用方依赖的行为和用户已有修改。
4. **实际验证**。按切片从入口验收到结果。运行相关构建、已有测试和必要的回归检查。新测试用于现有覆盖无法捕获的具体回归，或用户、仓库要求的场景。诊断失败，修复范围内的问题后重跑。记录实际命令或步骤、环境、观察结果和状态。受环境限制的检查写明阻塞原因，模拟环境的结论绑定到所测环境。
5. **文档交付**。按 [六节文档模板](references/delivery-template.md) 形成 Markdown 文件，保存到用户指定位置或仓库已有的交付文档目录。两者均未指定时使用 `docs/changes/<主题短名>.md`。对照最终代码和测试输出核对路径、行号、流程节点和验收。删除为了辩解或预防质疑写的句子，把影响读者判断的事实直接写清楚。最终回复提供文档链接、实际验证结果和仍需处理的事项。

## 标题

使用 `【{类型}】{业务线} - {仓库} - {主题}`。业务线取用户、知识库或项目文档中的名称，多个仓库名用 `/` 连接。类型优先用此次变更实际 Git commit 的前缀，保留 `fix`、`feat`、`feature`、`docs`、`test`、`refactor`、`chore`、`config` 等原写法。此次变更尚未提交时，从仓库近期提交中选择符合这次变更的前缀；仓库没有可用前缀时按变更性质选择。文档标题无需触发额外的提交或推送。

## chat 项目

- 业务线优先沿用用户或知识库的叫法。本地可按 [README](../../../README.md) 的「网页 AI 对话」填写，仓库名用 `chat`。查 [现有需求](../../../docs/requirements-backend.md)、[API 文档](../../../docs/api.md) 和 [认证架构](../../../docs/auth-architecture.md) 时只读与任务相关的部分。
- 按 [测试手册](../../../docs/testing.md) 选择与切片对应的用例。前端 TypeScript 变更从 `frontend` 运行 `npm run build`，核对生成资源。后端用 CMake 构建并从实际入口验收。共享网络层、HTTP 或 SSE 变更涉及 Reactor 和 Proactor 时，分别构建和运行受影响的用例。
- 涉及登录、存储或模型交互时，按测试手册使用隔离的 MySQL、Redis、SMTP 或模型上游。记录实际配置类型、网络后端和覆盖的场景，文档及测试证据中只保留脱敏数据。
